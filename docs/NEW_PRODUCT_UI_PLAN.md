# New Product UI Plan

Status: discovery only (no implementation changes)

Branch inspected: `new-product-ui`

## Current architecture

This repository is a recovered production Vite/React application assembled from browser bundles rather than an ordinary `src/` tree. `scripts/assemble-recovered.mjs` builds the deployable `dist/` shell by copying `extracted/index.html`, recovered JavaScript/CSS chunks, and `vendor-src` assets into the expected `/assets` and `/vendor` layout. `scripts/serve-recovered.mjs` serves that output locally. `package.json` contains the assembly, runtime-audit, HTTP checks, and PDF-operation tests; there is no conventional Vite source entrypoint, `vite.config.*`, or TypeScript application source directory.

The runtime entrypoint is `recovered/index-AX28eR3E.js` (copied to `dist/assets/index-AX28eR3E.js`). It imports the React vendor chunk and uses React lazy loading plus a Vite preload map for roughly 50 tool routes and dashboard/search surfaces. `recovered/react-vendor-Bc7KCos-.js` contains React, ReactDOM, and React Router. `recovered/index-C7wPnfL7.css` is the production stylesheet.

## UI layer

The primary UI/layout is embedded in `recovered/index-AX28eR3E.js`:

- global React application component and route/path selection;
- responsive sidebar, mobile header, workspace, suspense/loading state, notifications, dialogs, install prompt, and offline/service-worker behavior;
- navigation labels and sections (dashboard, scan/workflow, page management, collaboration, resources);
- tool registry metadata, descriptions, icons, keyword search data, and route aliases;
- lazy component map and switch that renders each selected tool;
- document title and local-storage/history state.

`extracted/assets/Dashboard-C3JB9zw0.js` (assembled as `dist/assets/Dashboard-C3JB9zw0.js`) is the dashboard/homepage card grid, FAQ, recent/history presentation, and dashboard-specific UI. It imports the main bundle's exported icon/helpers and `chevron-down-B25xREwk.js`. `recovered/ToolSearchModal-dkdd7EmT.js` is the search modal UI and search filtering surface. The production CSS chunk controls the visual system; most component styling is inline utility-class strings in the recovered bundles.

`extracted/index.html` is the document shell and contains the original title, metadata, PWA links, structured data, social cards, canonical URLs, and the original product's marketing copy and outbound links. It is copied unchanged as the starting HTML by the assembler (with generated-runtime substitutions applied later).

## Processing layer

Each recovered tool chunk is a self-contained React feature whose default export is mounted by the main bundle. Tool chunks perform transformations in the browser using File/Blob APIs, Canvas, Web Crypto, Web Workers, IndexedDB/localStorage, and browser libraries exposed by the vendored runtime. Representative integrations include:

- PDFLib/PDF.js for PDF parsing, rendering, and mutation;
- jsPDF, JSZip, XLSX, Mammoth, docx-preview, marked, and related office/document conversion libraries;
- Tesseract workers/language data for OCR;
- Transformers/Kokoro/ONNX assets for selected browser AI features;
- Ghostscript worker/WASM for the recovered compression/workflow path;
- WebRTC for intentional peer-to-peer share/whiteboard features.

The processing boundary is the props contract from the main bundle (`showNotification`, `showDownloadDialog`, and route/tool selection) plus browser globals and `/vendor` assets. The main UI chooses and mounts a tool; the tool owns file selection, processing, preview, and download. No application-owned upload backend was found. Chat with PDF is the explicit exception: its recovered feature sends extracted text/prompts to Gemini when invoked.

## Integration boundaries

Safe boundary for a new UI:

1. Keep the existing tool chunks and their exported default components.
2. Replace the shell/router/navigation/dashboard/search presentation that selects those components.
3. Preserve the selected tool ID/path mapping or provide an adapter from new routes to the existing IDs.
4. Continue passing the existing callback props and preserving the global/vendor asset paths generated by the assembler.
5. Keep `scripts/assemble-recovered.mjs` and its transformations unless the new entrypoint deliberately replaces the production assembly contract.

The strongest compatibility constraint is that dashboard currently imports helpers from the main bundle. Replacing the main bundle UI may require either retaining the helper exports or replacing Dashboard with a new component that does not import them. Likewise, recovered tools should not be rewritten merely to change labels or layout.

## Files that can be replaced safely (UI scope)

- A future source entrypoint and new application shell (not present yet).
- `extracted/index.html`, after preserving required script/style/PWA wiring and replacing original metadata.
- The UI portion of `recovered/index-AX28eR3E.js`, only when a new compiled shell can preserve its tool-loader contracts; avoid editing the recovered artifact directly during initial implementation.
- `extracted/assets/Dashboard-C3JB9zw0.js`, if replaced by a new dashboard that mounts the same tool IDs.
- `recovered/ToolSearchModal-dkdd7EmT.js`, if a new search surface uses the existing registry or an equivalent maintained registry.
- `recovered/index-C7wPnfL7.css`, if the new UI supplies its own stylesheet and no tool relies on global selectors (verify before removal).
- `scripts/assemble-recovered.mjs` only as the integration/build adapter after a new UI entrypoint exists.

These are candidate replacement points, not changes made in this phase.

## Files that should remain untouched

- All files under `recovered/` containing tool implementations, especially PDF operation chunks and `pdf-utils-DHnwt0li.js`.
- `recovered/react-vendor-Bc7KCos-.js` unless a deliberate dependency migration is separately approved.
- `vendor-src/**` runtimes, workers, WASM, fonts, OCR data, and model artifacts.
- `scripts/test-pdf-operations.mjs`, `scripts/verify-recovered.mjs`, and runtime URL/HTTP audits while preserving their coverage.
- `package.json`/`package-lock.json` compatibility-sensitive dependencies.

The baseline branch must remain unchanged; this branch should use additive adapters or new source files rather than altering baseline artifacts.

## Original branding/content to remove or replace

Static and executable references identify the original product as `ihatepdf`, `ihatepdf.cv`, and related claims such as “Free Online PDF Editor,” “No Upload,” “No Watermark,” “Works offline,” “46 tools,” and “Technical Blog.” The main bundle also contains the original logo treatment, dashboard/sidebar labels, FAQ copy, install prompt text, document titles, local-storage keys (`ihatepdf_*`), contact email, and a Clarity integration stub. The HTML contains:

- title, description, keywords, author/creator/publisher/copyright;
- canonical, alternate, Open Graph, Twitter, JSON-LD, FAQ, and HowTo metadata;
- original domain URLs and social/project links;
- Razorpay/payment link and directory/listing links;
- PWA application names and icon/manifest references;
- original marketing statements and reviews.

The new product should replace visible branding, titles, copy, metadata, logos/icons, contact/payment/marketing links, and product-specific storage namespaces. Keep only generic legal/provenance notices and third-party attribution where required. Do not carry over claims that no longer describe the new product (especially “no upload” if Chat/P2P features remain exposed).

## Tools currently exposed

The recovered registry exposes approximately 50 production tools: text/HTML/Markdown/Word/Excel/PPTX/EPUB/audio conversions; merge, split, compress, rotate, organize, crop/resize, watermark, page numbers, headers/footers, redact, encrypt/unlock/password removal, forms, OCR/extract/edit/repair, image/PDF conversions, compare/summarize/fingerprint/privacy, GST/POS utilities, scan, P2P share, collaborative whiteboard, and workflow. Exact IDs and paths are defined in the `Q`/`ho` maps in the main bundle and are also summarized in `RECOVERED_MODULES.md` and `LOCAL_EXTERNAL_AUDIT.md`.

## Recommended tools to keep

For a broadly useful original product, retain the validated local core first: Merge, Split, Compress, Rotate, Organize, Watermark, Page Numbers, Headers/Footers, Crop/Resize, Redact, Encrypt, Unlock/Remove Password, Fill Form, OCR, Extract Text, PDF-to-JPG, Images-to-PDF, PDF-to-Word, PDF-to-Excel, PDF-to-HTML, PDF-to-ZIP, Fingerprint, Repair, and the text/Markdown/office conversion tools. Keep Compare/Summarize/EPUB-AI/PDF-to-Audio only if the product is prepared to ship their large local models and clearly communicate resource requirements. Keep Workflow if its worker chain remains supported and test-covered.

## Recommended tools to remove or gate initially

Consider hiding or placing behind an explicit “experimental/network” area: Chat with PDF (Gemini API and external user-data path), P2P File Share, Collaborative Whiteboard, Audio-to-PDF Whisper model selection, and business-specific GST/POS tools if they do not fit the new product audience. These should be removed from navigation/registry exposure, not deleted from recovered files, until a product decision is made. Keep their chunks available for later reintroduction.

## Proposed new application structure

Create a normal source-owned UI layer around the preserved engine:

```
src/
  app/                 # root shell, route mapping, providers
  components/          # header, sidebar, command/search, dialogs, notifications
  pages/               # home, workspace, settings/about, optional tool catalog
  registry/             # curated product tool metadata -> recovered tool IDs
  engine/               # thin adapters; no PDF algorithm rewrites
  styles/               # new design tokens and layout styles
public/                 # new icons, manifest, static product assets
```

The adapter layer should dynamically import or otherwise mount the existing production chunks from the assembled asset layout. A first migration can retain the current assembly and introduce a new shell entry chunk; a later migration can compile preserved modules into a conventional Vite build only if that does not alter behavior. The new UI should own branding, navigation, route policy, feature gating, and copy while the engine remains an opaque compatibility surface.

## Risks and compatibility concerns

- The recovered main bundle combines UI, registry, lazy imports, icons, storage helpers, and some runtime behavior; separating it mechanically is risky.
- Dashboard imports exports from the main bundle, so replacing one without an adapter can break module loading.
- Relative lazy imports must continue resolving under `/assets`; the assembler/preload map is part of the runtime contract.
- Some tools expect browser globals, workers, fonts, WASM, model paths, or localStorage/IndexedDB state. New routing must preserve initialization order and asset URLs.
- Changing tool IDs or storage keys can strand existing history and cached documents; decide whether migration or intentional reset is desired.
- Removing original metadata from HTML must retain required module script, manifest, icons, and security headers.
- Chat, P2P, Whiteboard, and uncached Whisper are intentionally network-dependent; product copy and privacy UX must distinguish them from local-only processing.
- The repository contains recovered production artifacts with unresolved provenance/licensing review (notably Ghostscript and original chunks); a new product release needs rights review before redistribution.
- Existing dependency advisories are documented and should be handled in a separate compatibility-tested security pass, not during UI redesign.
- Automated PDF-operation, runtime URL, HTTP asset, and checksum tests must remain green after every UI integration step.
